# Звіт з практичної роботи №1: Моделювання даних і вибір підходу

### 1. Вибір предметної області
**Предметна область:** Служба доставки.

### 2. Опис предметної області
*   **Користувачі:** 
    *   *Клієнти:* створюють замовлення, оплачують їх, відстежують переміщення посилок.
    *   *Кур'єри/Водії:* отримують список замовлень на день, змінюють статуси доставки, планують маршрут.
    *   *Адміністратори (менеджери відділень):* контролюють завантаженість відділень, керують транспортом, розв'язують конфліктні ситуації.
*   **Об'єкти, які описує система:** Користувач (Клієнт або Кур'єр), Відправлення (Посилка), Замовлення, Відділення (склад), Маршрут (трекінг-запис).
*   **Операції:** Реєстрація користувача, створення нового замовлення, розрахунок вартості та термінів, призначення кур'єра, оновлення геолокації та статусу доставки, видача посилки, скасування замовлення.

### 3 та 4. Факти та сценарії (Таблиця «Об'єкт — Факт — Сценарій»)
Для аналізу обрано два сценарії: **«Створити нове замовлення»** та **«Оновити статус доставки»**.

| Об'єкт | Факт, який потрібно зберігати | Сценарій | Як змінюється/створюється |
| :--- | :--- | :--- | :--- |
| **Клієнт** | ПІБ, номер телефону, рейтинг | Створити нове замовлення | Використовується (або створюється, якщо клієнт новий) |
| **Замовлення** | Номер (ID), дата створення, вартість, статус (напр. «Створено») | Створити нове замовлення | Створюється новий факт |
| **Посилка** | Вага, габарити (ширина/висота/довжина), опис вмісту | Створити нове замовлення | Створюється новий факт |
| **Відділення** | Адреса, номер відділення, поточна місткість | Створити нове замовлення | Використовується (призначається пункт прийому) |
| **Замовлення** | Статус (напр. «В дорозі»), час останнього оновлення | Оновити статус доставки | Змінюється існуючий факт |
| **Кур'єр** | Поточна локація (GPS координати), статус зайнятості | Оновити статус доставки | Змінюється існуючий факт |
| **Маршрут** | Точка транзиту, мітка часу прибуття на склад | Оновити статус доставки | Створюється новий факт (історія переміщень) |

### 5. Порівняння моделей даних для служби доставки
1.  **Ієрархічна модель**
    *   *Сильна сторона:* Дуже швидкий доступ до посилок, якщо вони жорстко прив'язані до одного відділення (Відділення -> Список посилок).
    *   *Слабка сторона:* Неможливо адекватно описати, що одне замовлення одночасно пов'язане і з клієнтом, і з кур'єром, і з кількома транзитними складами.
2.  **Мережева модель**
    *   *Сильна сторона:* Дозволяє відобразити складні маршрути (склад пов'язаний з багатьма замовленнями, замовлення - з багатьма складами).
    *   *Слабка сторона:* Дуже складна розробка і підтримка; зміна структури логістики потребуватиме переписування всієї структури БД.
3.  **Реляційна модель**
    *   *Сильна сторона:* Гарантує цілісність даних (транзакції) — наприклад, при списанні коштів і зміні власника посилки не виникне розбіжностей.
    *   *Слабка сторона:* Для побудови повного звіту по маршруту однієї посилки знадобиться об'єднання багатьох таблиць (JOIN), що може сповільнювати роботу при великих навантаженнях.
4.  **Об'єктна модель**
    *   *Сильна сторона:* Легко описати різні типи відправлень (звичайна посилка, крихкий вантаж, документи) завдяки наслідуванню класів.
    *   *Слабка сторона:* Складно інтегрувати зі стандартними інструментами бізнес-аналітики, які зазвичай очікують табличні (реляційні) дані.
5.  **Документна модель (NoSQL)**
    *   *Сильна сторона:* Всю інформацію про замовлення (відправник, отримувач, вага, масив точок маршруту) можна зберігати в одному JSON-документі, що робить його завантаження дуже швидким.
    *   *Слабка сторона:* Важко гарантувати строгу структуру даних, складно будувати аналітичні запити (наприклад, "знайти середню вагу посилок по всіх відділеннях за рік").
6.  **Ключ-значення (Key-Value)**
    *   *Сильна сторона:* Ідеально підходить для миттєвого збереження тимчасових даних — наприклад, поточних GPS-координат кур'єра або сесії користувача в додатку.
    *   *Слабка сторона:* Неможливо зробити пошук за параметрами (наприклад, знайти всі замовлення зі статусом "Очікує видачі"), оскільки пошук працює тільки за точним ключем (ID).

### 6. Висновок про вибір моделі даних
Для розробки інформаційної системи служби доставки я обираю **реляційну модель даних** як основну. Вона найкраще підходить для цієї предметної області, оскільки забезпечує високу надійність транзакцій (властивості ACID), що є критично важливим для фінансових розрахунків та точного обліку замовлень. Завдяки нормалізації даних ми уникнемо дублювання інформації про клієнтів, кур'єрів та адреси відділень, що часто стається в документних базах. Ієрархічна та мережева моделі є технічно застарілими і не дадуть потрібної гнучкості для сучасної логістики. Хоча документну модель або базу "ключ-значення" було б зручно використати як допоміжні інструменти (для кешування або збереження поточних координат транспортних засобів), саме реляційна модель гарантує надійний баланс між цілісністю критичних бізнес-даних та гнучкістю SQL-запитів. Таким чином, реляційна база даних є найбезпечнішим та найбільш обґрунтованим вибором для ядра системи.
